# Wi-Fi 无线通讯兼容方案

> 目标：板子和电脑之间不再需要 USB 数据线（板子只接 5V 电源），macOS 与 Windows 都支持；同时 **USB 照旧可用**，新旧固件、新旧 bridge 互相兼容。
> 状态：已实现（见 [§15](#15-实现情况)）：第一期（2026-10-28）板子 → Mac、USB 自动配对、加密、USB / Wi-Fi 热切换；第二期（2026-10-29）电脑 → 板子（Windows 方向）、屏幕验证码配对、多台电脑与控制者规则。经 Wi-Fi 录屏还没做；OTA（§11、P3）决定不做。方案写于 2026-10-25，基于 v3.7.2（`5c915f3`）。

## 0. 结论速览

1. **bridge 仍然跑在电脑上**。hooks、statusline、magpie 网关（`127.0.0.1:3425`）、按键计数、键鼠空闲、系统 TTS 都只能在电脑本地拿到，所以要换的只是「bridge ↔ 板子」这段线缆，上层的 JSON 行协议原样保留。
2. **传输层用 TCP（端口 47824），一条连接上同时承载 JSON 行、录屏帧和语音**。连上后先认证，之后每帧用 AES-256-GCM 加密。
3. **两个方向都能建立连接**，因为两个平台的限制正好相反：
   - **macOS**：后台 launchd agent 主动连局域网要过「本地网络」隐私授权，而**接受入站连接不需要**（Apple TN3179）。默认让 **板子去连电脑**。
   - **Windows**：防火墙默认拦入站连接，弹窗授权要管理员权限，出站连接直接放行。默认让 **电脑去连板子**。
   - 连接建立后两种方向完全一样，固件和 bridge 上只多一个「拨号 / 监听」的分支。
4. **配对**：插着 USB 时一条命令完成，密钥走串口，物理接触可信。没插 USB 时用「屏幕验证码」配对（X25519 密钥交换，再对比 6 位码）。
5. **USB 优先、Wi-Fi 兜底、热切换**：插着线就走 USB（延迟最低，录屏最快）；拔线后 2 秒内切到 Wi-Fi，屏幕不会显示「未连接」。
6. **烧录固件第一、二阶段仍走 USB**（新版本才需要，频率很低）。OTA 放到第三阶段，要先把两套中文字体（共 655KB）挪到独立分区，4MB Flash 才放得下两个应用槽。
7. 分三个阶段做，见 [§12](#12-分阶段计划)。

## 1. 现状：USB 链路上跑着什么

`bridge/agent_bridge.py` 的 `Link` 类负责串口（VID 0x303A 自动找口，115200 波特率；USB CDC 实际不受波特率限制）。每行一个 JSON，每条自动附带 `now`（时间戳）和 `tz`（时区偏移）。

### 电脑 → 板子（`handleLine()`，`agent_buddy.ino:145`）

| 类型 | 内容 | 频率 / 大小 |
|---|---|---|
| `state` / `cx` | Claude / Codex 汇总状态 | 状态变化时发，每 30 秒全量重发；cx 每 5 秒一次；<300B |
| `usage` / `cusage` | 5h / 7d 额度 | 变化时发，至少每 60 秒一次；<200B |
| `mq` `mu` `mr` `ma` `mst` | magpie 四页数据 | 3~60 秒一次，变化才发；单条 1~2KB |
| `act` | 键鼠空闲秒数、电脑麦克风是否占用 | 每秒；<80B |
| `key` | 新按键数（只有次数） | 打字时每 0.1 秒；<50B |
| `back` | 离开后回来 | 偶发 |
| `sfx` / `au` | 音效名 / 语音 PCM（base64，每块 3000B 原始数据） | 播报时约 32KB/s 的 PCM，突发发送 |
| `ui` `gamma` `cap` `hello` | 调试、设置、录屏开关、问版本 | 偶发 |
| `ping` | 心跳 | 每 2 秒 |

### 板子 → 电脑（目前都是 `Serial.print*`）

| 输出 | 位置 | 用途 |
|---|---|---|
| `HELLO {"fw":…}` | `agent_buddy.ino:198` | `buddy.py` 判断固件版本 |
| `CFG {…}` | `ui_settings.ino:112` | 声音设置同步（以板子为准） |
| `PRES {…}` | `hw_radar.ino:454` | 雷达在座判断，bridge 用来判断你离开 / 回来 |
| `CXACC` | `agent_buddy.ino:723` | 点 Codex 额度卡切换账号 |
| `PERF` `SCAN` `MIC` `SPK` `RADAR` | 多处 | 调试日志 |
| 录屏帧 `A5 5A 'F' 'R'` + RLE | `sendFrame()`，`agent_buddy.ino:675` | 录屏 / 截图，和文字混在同一个字节流里 |

### 只有电脑能提供的东西（这些不受换 Wi-Fi 影响）

Claude Code / Codex hooks、statusline 额度、magpie 本地接口和 `magpie ls`、macOS `CGEventSourceCounterForEventType` / Windows 键盘钩子、电脑麦克风占用、`say` / SAPI 语音合成。**所以「全部走 Wi-Fi」= 去掉数据线，不等于去掉 bridge。**

板子仍需 5V 供电，任意 USB 充电头或充电宝都行。供电口插的是充电头（没有 USB 主机）时，固件的串口写入会直接丢弃，不会阻塞，见 §2.3。

## 2. 约束与调研结论

### 2.1 macOS：本地网络隐私（macOS 15 起）

Apple TN3179 的要点：

| 操作 | 是否需要「本地网络」授权 |
|---|---|
| 主动发起 TCP 连接到局域网地址 | **需要** |
| 监听并接受入站 TCP 连接 | **不需要** |
| 发 UDP 单播 / 组播 / 广播 | 需要 |
| 接收入站 UDP 单播 | 不需要 |
| 接收入站 UDP 组播 / 广播 | 需要 |
| 解析 `.local` 名字、Bonjour 注册 / 浏览 / 解析 | 需要 |

- 自动豁免的只有：launchd **daemon**、root 进程、**从终端 / SSH 运行的命令行工具及其子进程**。原文写明：daemon 的豁免不适用于 launchd agent。
- bridge 开机自启用的是用户级 LaunchAgent（`buddy.py` 里的 `PLIST`），**不豁免**。
- TN3179 说本地网络隐私按代码签名识别程序，ad-hoc 签名会不可靠。本机 venv 的 Python 来自 uv（`~/.local/share/uv/python/cpython-3.13-…`）。论坛上有用 Homebrew 这类 ad-hoc 签名二进制的案例：LaunchAgent 里连局域网直接报 `EHOSTUNREACH`（No route to host），**不弹授权框**（Apple 论坛 thread 778457）。
- 从终端手动 `buddy start` 也许没问题（终端豁免），一旦改成开机自启就会出问题，而且没有任何提示。这种故障最难排查。

**结论**：在 macOS 上让 bridge **监听**，板子主动来连，这样完全绕开授权问题。`buddy pair` 在终端里运行（属于豁免），可以主动连板子做配对。

另外两点：
- macOS「应用防火墙」默认关闭；用户打开了的话，监听时会弹「是否允许接受传入连接」。setup 用 `socketfilterfw --getglobalstate` 检测，开着就提示。
- macOS 15.5 起可以用 `AllowedWiFiLocalNetworkAddresses` 把某个网段整体豁免，但要 sudo 加重启，影响全系统，**不采用**。

### 2.2 Windows：Defender 防火墙

- **出站**连接默认全部放行，不弹窗，也不需要管理员权限。
- **入站**：程序第一次监听非回环地址时，系统会弹「Windows 安全中心警报」，允许需要管理员确认。bridge 用 `pythonw` 在后台运行，弹窗容易被忽略或被点掉；一旦点了取消，系统会为 python.exe 写一条**拦截规则**，之后一直静默失败。
- 家里的 Wi-Fi 常被识别成「公用网络」，入站规则和 mDNS 的行为又会再变一层。

**结论**：Windows 上由 **电脑去连板子**，setup 仍然不需要管理员权限，和现在一致。

### 2.3 ESP32-S3 侧

**HWCDC 背压（实际风险，已查源码确认）。** 当前 core 是 esp32 3.3.12，`HWCDC::write` 的行为如下：
- **没有 USB 主机**（只插充电头）：数据进环形缓冲，满了按先进先出丢掉，**不阻塞**。
- **插在电脑上，但没有程序读串口**（例如 bridge 已经切到 Wi-Fi，串口没人打开）：被当成「主机背压」，每次写最多等 `20 × tx_timeout`。固件里设的是 `setTxTimeoutMs(200)`，也就是**单次写最多卡 4 秒**，主循环跟着卡住，画面冻结。
- 所以要求：**输出只写当前活跃的那条链路**。当前链路是网络时不写 `Serial`；必须写的调试输出先检查 `Serial.availableForWrite()`。

**Wi-Fi 省电。** 默认的 modem sleep 会让下行延迟受路由器 DTIM 影响，抖到 100~300ms，打字跟手动画会明显变慢。有会话连着时调用 `WiFi.setSleep(false)`。板子本来就是外接供电，耗电不是问题。

**核心占用。** 刷屏任务 `flushLoop` 固定在 core 0、优先级 1。Wi-Fi / lwIP 任务也在 core 0，优先级更高。平时流量小，影响可以忽略；录屏时流量会到每秒 MB 级，可能挤占刷屏时间。网络任务要用独立的 FreeRTOS 任务配合非阻塞 socket，**主循环永远不等网络**。

**内存。** Wi-Fi 已经以 STA 模式启动（`wifiInit()`），驱动的常驻开销已经算在现有内存里了。新增的是 lwIP 收发缓冲、2~3 个 socket、GCM 上下文，估计内部 RAM 再多 20~40KB。大块缓冲（收发环形缓冲、录屏帧）放 PSRAM。实现后用 `heap_caps_get_free_size(MALLOC_CAP_INTERNAL)` 实测。

### 2.4 Flash 与 OTA 空间（实测）

- Flash 4MB，当前分区方案 `huge_app` 只有一个 3MB 应用槽，没有 OTA。
- `firmware/app.bin` = **1,978,096 B**。
- 从链接 map 文件看，两套中文字体占了约 1/3：`u8g2_font_cubic11_h_cjk` 337,650 B，`u8g2_font_unifont_h_chinese4` 317,506 B，**合计 655KB**。
- 标准的双 OTA 布局（每槽 0x1F0000 = 2,031,616 B）只比现在的固件大 53KB，加上网络代码以后就放不下了。
- **办法**：两套字体放进一个独立的数据分区，用 `esp_partition_mmap` 映射成指针交给 u8g2，两个应用槽共用。这样每个应用槽约 1.33MB，1.5MB 的槽就够用（详见 §11）。

### 2.5 网络环境

- ESP32-S3 只支持 **2.4GHz**。电脑连 5GHz 没关系，只要和板子在同一个局域网。
- **访客网络 / AP 隔离**（酒店、公司、部分路由器默认开启）会禁止设备之间互访，这种情况下只能用 USB。`buddy status` 要能检测出来并说明原因。
- 企业 802.1X（WPA2-Enterprise）：板子的 Wi-Fi 界面目前不支持，不在本方案范围。
- DHCP 可能给板子或电脑换 IP，所以寻址不能只依赖缓存的 IP（§6）。

### 2.6 备选方案对比

| 方案 | 不选的原因 |
|---|---|
| **BLE** | 不经过路由器，没有 AP 隔离问题；但 macOS 上后台 Python 用蓝牙同样要 TCC 授权，问题和本地网络授权类似；吞吐约 50~100KB/s，录屏很勉强；和 Wi-Fi 共用射频；NimBLE 还要再占几十 KB 内存。可以作为以后的补充选项。 |
| MQTT | 要多装一个 broker，用户多一个服务要维护。 |
| HTTP / WebSocket（板子做服务端） | 每条消息都有协议开销，而且 Windows 要监听时仍然有入站问题。现有协议本来就是「行」，用裸 TCP 最贴合。 |
| ESP-NOW | 电脑那端要额外接一块 ESP32 当网卡，等于又插回 USB。 |
| TLS-PSK | Python 3.13 起才有 PSK 回调，用户电脑上的 Python 版本没法保证；板子每条连接还要 30~40KB 内存。自己做 AEAD 帧更轻。 |

## 3. 总体架构

```
                 ┌────────────── 电脑（macOS / Windows）─────────────┐
Claude Code ─hooks─▶ bridge  HTTP 127.0.0.1:47823（不变，只听本机）  │
Codex ──────hooks─▶   │                                              │
statusline ───────▶   ├── SerialLink（USB，现有）                    │
magpie 网关 ◀─读────  ├── NetLink（Wi-Fi，新增）                     │
                      │     macOS：监听 0.0.0.0:47824，等板子来连     │
                      │     Windows：主动连 板子:47824               │
                      └── LinkManager：挑当前链路，USB 优先 ─────────┘
                                   │ USB                │ Wi-Fi（TCP + AES-GCM）
                                   ▼                    ▼
              ┌──────────────── ESP32-S3 ────────────────────────────┐
              │ pollSerial() ─┐                                       │
              │ pollNet()  ───┴─▶ handleLine()（不变）               │
              │ netTask（core 0）：监听 47824 / 拨号到电脑 / 握手 / 加解密 │
              │ hostOut()：CFG / PRES / CXACC / HELLO / 录屏帧 → 当前链路 │
              └───────────────────────────────────────────────────────┘
```

设计原则：
- **上层协议一个字节都不改**。`handleLine()`、`device_line()`、各种消息类型保持原样，只把「从哪收、往哪发」抽成一层。
- **认证之后，两个连接方向完全对称**。谁先拨号只决定连接由谁发起。
- **USB 永远可用**，而且是可信通道：配对、写密钥这类敏感操作**只能**从串口执行。

### 连接方向怎么选

| 平台 | 默认 | 原因 | 备用 |
|---|---|---|---|
| macOS | 板子 → 电脑（bridge 监听 47824） | 入站不需要本地网络授权，LaunchAgent 下也稳定 | 电脑 → 板子（授权过以后可用） |
| Windows | 电脑 → 板子（板子监听 47824） | 出站不过防火墙，不需要管理员 | 板子 → 电脑（要手动加入站规则） |

`state/device.json` 里的 `mode` 可以设为 `auto` / `listen` / `dial`，`auto` 按上表选。也可以用环境变量 `AGENT_BUDDY_LINK=usb|wifi|auto` 临时覆盖。

## 4. 线协议

### 4.1 握手（明文，只用来认证）

板子记为 B，电脑记为 H。TCP 连上以后，不管谁先拨号：

```
B → H:  BUDDY/2 <board_id> <nB>\n                 nB：16 字节随机数（hex）
H → B:  HOST <host_id> <nH> <macH>\n              macH = HMAC-SHA256(K, "H" | board_id | nB | nH)
B → H:  OK <macB>\n                               macB = HMAC-SHA256(K, "B" | host_id | nH | nB)
        （失败：ERR <原因>\n，然后断开）
```

- `board_id`：MAC 地址后 3 字节，例如 `a1b2c3`，也用在主机名 `agent-buddy-a1b2c3` 里。
- `host_id`：配对时生成的随机 8 字节；`K` 是这台电脑和这块板子共有的 32 字节密钥。
- 板子按 `host_id` 在 NVS 里找 `K`。找不到，或者 HMAC 不对，就回 `ERR` 断开，并对来源 IP 退避（1 秒、2 秒、4 秒……最长 60 秒）。
- 双方都验证对方的 MAC，只有持有 `K` 的一方能通过；两边都出了随机数，所以录下来重放无效。

### 4.2 会话密钥与加密帧

```
k_h2b = HKDF-SHA256(K, salt = nB | nH, info = "buddy h2b")
k_b2h = HKDF-SHA256(K, salt = nB | nH, info = "buddy b2h")

帧：  u32 长度（小端，不含自身） | AES-256-GCM 密文 | 16 字节 tag
nonce： 4 字节方向常量 | u64 计数器（每帧加 1，不在线上传输）
明文：  u8 记录类型 | 数据
```

| 记录类型 | 内容 | 对应现在的什么 |
|---|---|---|
| `0x01` | 一行 JSON（不带 `\n`） | 串口上的每一行，双向 |
| `0x02` | 录屏帧：u32 millis + RLE 数据 | `A5 5A 'F' 'R'` 帧，网络上不再需要魔数切分 |
| `0x03` | 语音 PCM 原始字节 | 现在的 `au` + base64，可选，省三分之一流量 |
| `0x04` | 板子心跳（空） | 新增：板子每 2 秒发一次，电脑 10 秒收不到就判断断线 |

- 收到计数器不连续、或 tag 校验失败的帧，直接断开连接。没有重放窗口，TCP 本身保证顺序。
- 单帧上限 512KB，最坏情况的 RLE 帧是 480×272×3 = 391,680 B。
- 两端都设置 `TCP_NODELAY` 和 TCP keepalive。
- 实现：Python 用 `cryptography` 包（`AESGCM`、`HKDF`、`X25519`，macOS arm64 / x86 和 Windows 都有预编译 wheel），加进 `requirements.txt`。板子用 IDF 自带的 mbedTLS（`mbedtls_gcm_*` 走 S3 硬件 AES；`mbedtls_md_hmac`；HKDF 用 HMAC 自己写几行就行；`mbedtls_ecdh` 的 Curve25519）。

### 4.3 版本协商（向后兼容的关键）

新固件的 `HELLO` 多带几个字段，老字段不变：

```
HELLO {"fw":"v3.8.0","proto":2,"net":1,"id":"a1b2c3","ip":"192.168.1.50","wifi":"MyHome","paired":2}
```

- bridge 看到没有 `proto` 字段（老固件），就只走 USB，`buddy status` 提示升级固件。
- 老 bridge 连新固件：只会走 USB，新固件的串口行为完全不变，照常工作。

## 5. 配对与安全

### 5.1 威胁模型

局域网里的其他设备（室友的电脑、公司网络、中毒的 IoT 设备）可能会：
- **伪造状态、让喇叭说话、改设置**：`ui`、`au` 消息都能做到。→ 靠认证防住。
- **偷看内容**：状态里有 prompt 片段和命令行（已经打过码）、邮箱、额度，录屏帧就是整块屏幕。→ 靠加密防住。
- **冒充板子，骗 bridge 把数据发过去**：→ 双向 MAC 认证，冒充者没有 `K`。
- **反复尝试**：→ 板子按 IP 退避；没有密钥的连接不会得到任何数据。

不在范围内：能物理接触板子的人（USB 本来就是可信通道）、能控制电脑的人。

### 5.2 USB 配对（首选，覆盖绝大多数用户）

```bash
bridge/buddy pair          # 插着 USB 时
```

1. bridge 生成 `host_id` 和 `K`，从串口发 `{"t":"pair","id":…,"name":"小明的 MacBook Pro","k":<base64>,"dial":["Xiaoming-MBP.local","192.168.1.23"],"port":47824}`。
2. 板子写进 NVS 命名空间 `pair`（最多 4 台电脑，满了替换最久没连的），弹提示「已与 小明的 MacBook Pro 配对」。
3. bridge 把 `board_id`、`K`、板子 IP、`mode` 写进 `bridge/state/device.json`（macOS 权限 0600；Windows 放在用户目录，继承当前用户的权限）。
4. **固件只接受从串口来的 `pair` 消息**，网络来的一律忽略。网络上的连接永远没法改密钥。

`setup.sh` / `setup.ps1` 发现板子已经连上 Wi-Fi（`HELLO` 里有 `ip`）时，顺带问一句「配对 Wi-Fi，以后可以拔掉数据线？[Y/n]」。

### 5.3 屏幕验证码配对（没有 USB 的电脑，例如第二台 Windows）

1. 在板子上进入 设置 → 电脑 → **添加电脑**，打开 2 分钟的配对窗口。窗口外的配对请求一律拒绝。
2. 在电脑上运行 `buddy pair --wifi`，bridge 找到板子（§6），两边交换 X25519 公钥：`PAIR <host_name> <pubH>` ↔ `PAIRED <pubB>`。
3. 两边各自算 `SAS = HMAC(共享密钥, "sas") mod 10⁶`。板子屏幕和终端同时显示 6 位验证码，板子上有「允许 / 拒绝」按钮。
4. 用户看到两边数字一样，在板子上点「允许」，双方再用 `K = HKDF(共享密钥, "buddy pair")` 得到长期密钥。
5. 中间人没法让两边的验证码同时对上（和蓝牙的数字比较配对是同一个原理）。
6. macOS 上 `buddy pair` 是从终端运行的，属于豁免，可以主动去连板子。配对成功后，bridge 把自己的 `dial` 地址告诉板子，之后照常由板子来连电脑。

### 5.4 管理

- 板子 设置 → 电脑：列出已配对的电脑（名字、上次连接时间、当前是否连着），可以逐个移除。
- `buddy unpair`：删除本机的 `device.json`；插着 USB 时同时让板子删掉这台电脑的记录。
- 恢复出厂（`buddy flash --erase`）会清空 NVS，配对也一起清掉。

## 6. 发现与寻址

### Windows（电脑 → 板子），依次尝试

1. **缓存的 IP**（`device.json`）。直接连，成功就结束。
2. **USB 告知**：插着 USB 时，`HELLO` 里的 `ip` 字段，顺便刷新缓存。
3. **`.local` 名字**：`getaddrinfo("agent-buddy-a1b2c3.local")`。Windows 10 1709 起系统 DNS 客户端支持 mDNS 解析，由系统服务完成，不经过 Python 的防火墙规则。板子用 `ESPmDNS` 注册主机名和 `_agentbuddy._tcp` 服务。
4. **UDP 探测**：向各网卡的广播地址发 `BUDDY? <board_id>`，板子单播回 `BUDDY! <board_id> <port>`。Windows 防火墙默认放行「对广播的单播回应」（3 秒内有效）。
5. **子网扫描兜底**：对本机所在的 /24 网段并发尝试 TCP 连接 47824（254 个地址，约 1~2 秒），全是出站，不涉及防火墙。
6. 全都失败：`buddy status` 显示「同一网络里找不到板子：可能是访客网络 / AP 隔离，请插 USB」。

### macOS（板子 → 电脑）

1. 板子按配对时拿到的 `dial` 列表依次尝试：先缓存的 IP，再 `Xiaoming-MBP.local`。主机名由 macOS 的 mDNSResponder 回答，这是系统服务，和 bridge 的授权无关。板子用 `MDNS.queryHost()` 解析。
2. bridge 每次连上都把自己最新的 IP 发给板子（`{"t":"net","dial":[…]}`），板子更新 NVS。
3. 全都失败时，板子每 5 秒重试一次，设置页显示「找不到 Xiaoming-MBP，请确认 bridge 在运行、两边在同一网络」。

### 重连节奏

- 断线后按 1、2、5、5…… 秒退避；Wi-Fi 刚重连上时立刻重试一次。
- 电脑休眠时 bridge 停止，和 USB 时一样，板子 10 秒后显示「未连接」。

## 7. 多链路共存与切换规则

### 同一台电脑，USB 和 Wi-Fi 都通

- bridge 的 `LinkManager` 同时维护两条链路，**所有消息只从一条发**：串口打开了就走 USB，否则走 Wi-Fi。
- Wi-Fi 连接平时保持着，但只发心跳。拔掉 USB 后，下一次 `send()`（最多 0.2 秒内）就切过去，并按「新连上」的逻辑全量重发一次（等同 `pump()` 里 `was_connected` 从假变真）。
- 板子：网络是当前链路时，不往 `Serial` 写东西（§2.3 的背压问题）；`Serial` 一收到数据，就把当前链路切回 USB。

### 两台电脑（例如 Mac 用 Claude Code、Windows 用 Codex）

- **第一版：同一时间只有一个「控制者」**，避免两台电脑的 `state` 互相覆盖，屏幕来回跳。
  - 优先级：USB 那台 > 设置页里选定的「首选电脑」 > 先连上的那台。
  - 不是控制者的连接：板子回 `{"t":"role","r":"standby"}`，bridge 收到后只发心跳。控制者断开后，板子发 `role: active` 给下一台。
  - 设置 → 电脑 里可以手动指定控制者。
- **以后可以扩展：按来源合并**。板子按 `host_id` 分别保存 Claude / Codex 的状态，按 bridge 里 `PRIORITY` 的同一套规则挑出最高的显示。按键、离开 / 回来事件按控制者取。这需要把 `aggregate()` 的一部分逻辑搬进固件，第一版不做。

## 11. 固件升级：短期走 USB，长期 OTA

**短期**：`buddy flash` 不变。固件只在发新版本时才需要烧录，到时候插一次线就行。`buddy status` 发现固件比 `firmware/` 里的旧时提示插线升级。

**长期 OTA（第三阶段）**：

1. 新分区表。NVS 位置不变，**设置和配对都会保留**：

   ```
   # Name,   Type, SubType,  Offset,   Size
   nvs,      data, nvs,      0x9000,   0x5000
   otadata,  data, ota,      0xe000,   0x2000
   app0,     app,  ota_0,    0x10000,  0x180000   # 1.5MB
   app1,     app,  ota_1,    0x190000, 0x180000   # 1.5MB
   fonts,    data, 0x40,     0x310000, 0xE0000    # 896KB ≥ 两套字体 655KB
   coredump, data, coredump, 0x3F0000, 0x10000
   ```

2. 两套 u8g2 字体从编译进程序改成放在 `fonts` 分区：`esp_partition_mmap()` 拿到指针后交给 `setFont()`。u8g2 读字体就是普通的内存读，映射后的 Flash 一样可以读。用 `tools/` 下的脚本生成 `fonts.bin`，带版本号和 CRC，固件启动时校验，校验失败就退回一个内置的小英文字体并提示。
3. OTA 数据走**已经认证、加密的那条连接**：`{"t":"ota","size":…,"sha256":…}`，后面跟数据记录。板子用 `Update` 库写入非当前槽，校验通过后切换启动槽；新固件启动 60 秒内没能连上 bridge 就自动回滚（`esp_ota_mark_app_valid_cancel_rollback`）。这样不需要 ArduinoOTA，ArduinoOTA 要电脑开端口等板子回连，又会碰上 Windows 入站问题。
4. 从 `huge_app` 换到新分区表，需要**最后插一次 USB** 用 `buddy flash` 完成（同时写分区表、字体分区、应用）。
5. 风险：字体映射之后的读取性能要实测。Flash 走 cache，应该和现在 rodata 在 Flash 里的情况一样。

## 12. 分阶段计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0 传输抽象**（不改行为） | 固件：`hostOut` 路由、`pollSerial` 和 `handleLine` 解耦；bridge：`Link` 拆分出 `LinkManager`，只有 `SerialLink` | USB 下所有功能回归一遍：状态、magpie、语音、录屏、雷达、设置同步、`buddy status/flash` |
| **P1 电脑 → 板子 + USB 配对 + 加密** | `netTask` 服务端、mDNS、UDP 探测、握手 / AES-GCM；`buddy pair`；Windows 寻址链；`HELLO` 新字段；USB / Wi-Fi 热切换 | Windows：拔掉数据线（只接充电头），所有功能正常；插拔数据线时屏幕不出现「未连接」；抓包只能看到密文；没配对的客户端连不上 |
| **P2 板子 → 电脑 + 验证码配对 + 多电脑** | 板子拨号、`dial` 列表、bridge 监听；屏幕验证码配对；设置页「电脑」分区；控制者规则 | macOS 用 launchd 自启、重启电脑后不碰终端，Wi-Fi 也能自动连上；第二台电脑不插 USB 也能配对；Mac + Windows 同时在线时屏幕不来回跳 |
| **P3 OTA**（可选） | 字体分区、新分区表、经认证连接的 OTA、自动回滚 | `buddy flash --ota` 无线升级成功；升级中途断电不会变砖；设置和配对都保留 |

建议先做 P0 + P1，这时 Windows 已经能完全无线。macOS 在 P1 里也能用「电脑 → 板子」方向先跑起来：从终端运行 `buddy start` 属于豁免，launchd 自启下能不能用要看授权。P2 再把 macOS 的默认方向切成板子来连电脑，彻底解决。

## 13. 风险与需要实测的项

| # | 风险 | 应对 / 怎么验证 |
|---|---|---|
| 1 | HWCDC 背压：插着电脑但串口没人读时，每次写最多卡 4 秒 | 网络是当前链路时不写 `Serial`；或者先查 `availableForWrite()`。测法：插 Mac、bridge 走 Wi-Fi、打开 `perf=1` 看帧时间 |
| 2 | 录屏时 Wi-Fi 和刷屏任务抢 core 0 | 看 `PERF` 的 flush / fps；不行就把网络任务固定到 core 1 的低优先级，或者限制录屏帧率 |
| 3 | 内部 RAM 不够 | 实现前后对比 `heap_caps_get_free_size(MALLOC_CAP_INTERNAL)`；lwIP 缓冲按需调小 |
| 4 | macOS 打开了应用防火墙 | setup 检测并提示；用 uv 的 Python 时防火墙按路径记规则，换 Python 版本后要重新允许 |
| 5 | Windows 网络被识别为「公用」时 `.local` 解析失败 | 有 UDP 探测和子网扫描兜底；`buddy wifi` 诊断时提示网络类型 |
| 6 | 访客网络 / AP 隔离 | 无法解决，诊断出来后提示改用 USB |
| 7 | DHCP 换了 IP | 缓存 → `.local` → 探测 → 扫描，并且每次连上都刷新缓存 |
| 8 | 2.4GHz 干扰大时延迟抖动 | 状态类消息本来就有 30 秒全量重发；`key` 丢几下只影响动画 |
| 9 | 自己设计的加密协议出错 | 只用标准件（HMAC-SHA256、HKDF、AES-GCM、X25519）；计数器 nonce 不复用（每个会话重新派生密钥）；写对向测试：Python 和固件用同一组固定向量 |
| 10 | OTA 改分区后，旧版 `buddy flash` 写入地址不对 | `manifest.json` 本来就记录各部分的烧录地址，新版本把 `fonts.bin` 加进 `parts` 即可；旧版 bridge 读新 manifest 也能正确烧录 |

| 项目 | 状态 | 说明 |

| 录屏 | 只走 USB | Wi-Fi 下请求录屏会提示插 USB；超过 16000 字节的行在 Wi-Fi 下丢弃 |
| 电脑 → 板子（Windows） | 已做（第二期） | 板子同时监听 47824、注册 `agent-buddy-<id>.local` 和 `_agentbuddy._tcp`、回 UDP 探测（`BUDDY? <id\|*>` → `BUDDY! <id> <port> <配对窗口 1/0>`）。bridge 的 dial 模式依次试上次的 IP、`.local`、UDP 广播；没做 §6 的子网扫描兜底。被板子拒绝后隔 30 秒再试 |
| 屏幕验证码配对 | 已做（第二期） | 按 §5.3，细节：电脑发 `PAIR <host_id> <公钥> <port> <名字 base64> <地址\|->`，板子回 `PAIRKEY <公钥>`；验证码 = HMAC(共享密钥, `sas\|board_id\|nB\|PAIR 整行\|板子公钥`) 前 4 字节 mod 10⁶，所以名字和地址也被验证码覆盖；K = HKDF(共享密钥, salt = 电脑公钥 \| 板子公钥, "buddy pair")。有请求时板子自动跳到「电脑」页 |
| 多台电脑 | 已做（第二期） | 板子最多 4 台（NVS `pair` 里 h0~h3 等，v3.9 的单台记录开机自动迁移），每条连接一个任务，最多同时 3 条。控制者按 §7：USB > 首选 > 先连上的；角色用 `{"t":"role"}` 通知，待命连接的行双向都不处理。bridge 侧一台电脑仍只配一块板子（`device.json`） |
| OTA | 不做 | 烧录固件仍用 `buddy flash` 走 USB |
